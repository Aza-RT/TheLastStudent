# Windows build and run

## Prerequisites

- Windows x64 and an OpenGL 3.3-capable driver.
- Visual Studio 2022 or Build Tools 2022, **Desktop development with C++**, MSVC x64 and a Windows SDK. The same C++17 sources were locally verified with VS 2026 / MSVC 19.51; VS 2022 is the documented compatible generator, not a separately tested host.
- CMake 3.24+ (CMake 4 works; legacy dependency policies are handled).
- Python 3.10+ on PATH, for godot-cpp bindings generation.
- **Godot 4.7.2 standard x64 editor/binary**. The .NET edition is unnecessary.
- Internet for the first configure. CMake downloads version/commit-pinned archives, verifies SHA-256, and caches them in `native/third_party/`. No vcpkg, SCons, global GL headers, or package manager is required.

## Complete build

Run in the repository root, in PowerShell. A Developer PowerShell is optional with the Visual Studio generator.

```powershell
cmake -S . -B build -G 'Visual Studio 17 2022' -A x64 -DTLS_BUILD_EXTENSION=ON
cmake --build build --config Release --parallel 6
ctest --test-dir build -C Release --output-on-failure
```

Equivalent helper: `./tools/build.ps1`. If script execution is restricted, use `powershell -ExecutionPolicy Bypass -File tools/build.ps1`, or use the three direct commands above. Do not reuse a build directory configured for a different generator; use `-B build-vs2022` in that case.

VS 2026 users: `-G 'Visual Studio 18 2026'`. `Debug` is supported; all targets use the same static MSVC runtime to avoid CRT mismatches.

Outputs:

| Target | Output |
|---|---|
| gfxcore | `build/Release/gfxcore.lib` |
| gl_testbench | `build/Release/gl_testbench.exe` |
| tls_extension | `game/bin/tls_extension.dll` |
| tls_tests | `build/Release/tls_tests.exe` |

Shaders under `native/shaders/` are embedded from their source by CMake. Editing them automatically reconfigures the build. There are no shader paths baked into the DLL. The standalone development executable uses an absolute source atlas path, so rebuild it after moving the checkout; distribute it with the source checkout or add your own install packaging.

## Godot import and play

```powershell
$godotExe = 'C:\Tools\Godot_v4.7.2-stable_win64_console.exe'
& $godotExe --version
& $godotExe --headless --path game --editor --import --quit
& $godotExe --path game --rendering-method gl_compatibility
```

The version must start with `4.7.2.`. The helper checks this: `./tools/run.ps1 -Godot $godotExe`. `GODOT_BIN` is also supported. The development machine has a locally discovered binary in `.tools/`; that ignored folder is not provided by a clean checkout.

Open the editor with `& $godotExe --editor --path game`, or `./tools/run.ps1 -Godot $godotExe -Editor`. Press F6/F5 normally. Keep **Compatibility** selected; Vulkan, Mobile and D3D12 are not valid for the raw GL extension. Close the running game/editor before rebuilding the DLL because Windows locks loaded libraries.

Press F4 in play to compare the explicit native-texture fallback. It is also available with:

```powershell
& $godotExe --path game -- --fallback
```

or `tools/run.ps1 -Godot $godotExe -Fallback`. A native GL initialization failure changes to fallback automatically and is visible in F3 stats. Fallback still requires the built DLL; there is no GDScript replacement for the C++ AI.

## Individual targets

Without Godot bindings:

```powershell
cmake -S . -B build-gl -G 'Visual Studio 17 2022' -A x64 -DTLS_BUILD_EXTENSION=OFF
cmake --build build-gl --config Release --target gl_testbench tls_tests --parallel 6
ctest --test-dir build-gl -C Release --output-on-failure
.\build-gl\Release\gl_testbench.exe
```

Extension-only build: configure with `-DTLS_BUILD_TESTBENCH=OFF` and build `--target tls_extension`. `gfxcore` has no Godot dependency; `TLS_BUILD_EXTENSION=OFF` prevents fetching godot-cpp.

## Exact engine bindings and loader choice

`native/extension/extension_api.json` was generated by the installed `4.7.2.stable.official.ed1daf0bf` binary using `--headless --dump-extension-api`. It includes its exact engine version, types, method hashes and sizes. The pinned godot-cpp generator supports the 4.7 API. Its build profile trims unused engine classes while preserving referenced bases/built-ins.

There was no advertised `godot-4.7.2-stable` binding tag during implementation. We use the 4.7-capable upstream commit plus the exact custom API; the extension compiled, registered all four classes and ran in this exact engine. Do not replace the dump or pin with a 4.3/4.5 API. If your 4.7.2 build differs, generate its API in a temporary directory and compare before replacing the tracked file. A future engine migration requires intentional regeneration and retesting.

GLEW 2.2 initializes entry points against the **already-current** render-thread Compatibility context. It never creates a second context. GLFW creates the standalone app's context. `frame_post_draw` dispatches through `RenderingServer.call_on_render_thread`; a mutex guards frame snapshots. `GLStateGuard` restores every GL state our renderer changes; destruction is dispatched to the same render thread and synchronized before the node exits.

## Verification / captures

```powershell
.\tools\smoke.ps1 -Godot $godotExe -Visual
& $godotExe --path game --disable-vsync -- --benchmark
& $godotExe --path game --disable-vsync -- --fallback --benchmark
```

`artifacts/` is created by the smoke helper; create it first if invoking the capture/benchmark modes directly. `--capture` saves menu, raw gameplay, debug matrices, fallback, inventory and staged ending PNGs, then exits. `--benchmark` warms up 120 frames and measures 600 frames without the VSync cap. These modes are developer tools and do not change normal play.

The testbench `--smoke` verifies a deliberately modified GL state round trip, renders 90 frames, saves `testbench.ppm`, waits for GPU completion and exits. The CTest executable needs no GL context/window.

## Regenerate original assets

Generated files are already tracked. Optional regeneration:

```powershell
python -m pip install Pillow
python tools/generate_assets.py
python tools/generate_audio.py
python tools/generate_world.py
```

The first writes the atlas and original bitmap glyph sheet. Audio uses Python's standard library. World generation rewrites the editable map/items/dialogue JSON, so preserve intentional data edits before running it. Reimport in Godot afterward. Source data is not generated during a normal build.

## Troubleshooting

- Unknown `TLSShadeAI`/`TLSLightingRenderer`: build the DLL first, then run the editor import. Check `game/bin/tls.gdextension` and x64 architecture.
- LNK2038 runtime mismatch: reconfigure all dependencies in a fresh build directory; all targets must use the same MSVC runtime. Do not mix old standalone-only artifacts with a differently configured toolchain.
- CMake download/hash failure: retry with a working GitHub connection; keep the pinned hashes. No dependency installation is needed.
- Dark/incorrect graphics on another driver: press F4 and record F3 stats. Report the GL error, GPU, resolution and active path.
- Standalone atlas missing after moving the checkout: reconfigure/rebuild so `TLS_ASSET_DIR` points at the new source tree.

The intended deliverable is a buildable source checkout plus the Godot project and standalone demonstration. A signed installer/export-template bundle is outside the repository deliverable.
